Post-ship code review found 16 defects across the bootstrap feature; backend owned B1-B10 (frontend agent fixed the UI ones in parallel, coordinated via the coordinator, no direct SendMessage needed since no shared-contract questions came up). All landed on branch `feature/project-claude-bootstrap`, following [[project_bootstrap_step5_2026_07_11]].

**Key design decisions, in case this area gets touched again:**

- **B4 (approve dead-end) + B7 (pending contract) together changed the mental model**: once `entry.run.plan` is non-null, `onTurnComplete` NEVER demotes to `waiting_for_input` again (even for a no-op discuss turn) — it always re-enters `awaiting_approval`. Combined with `approveBootstrapPlan` now accepting both statuses whenever a plan exists, `waiting_for_input` is now ONLY reachable on the very first turn before any plan exists at all. This makes the two statuses almost synonymous once a plan is drafted — intentional, not an oversight; don't "simplify" one away without re-checking both call sites.
- **B7**: `approveBootstrapPlan` promotes any proposal absent from `decisions` AND still `pending` to `accepted` — previously these were silently left `pending` forever (dispatch only touches `accepted`). This is the ACTUAL enforcement of the "pending = implicitly included" contract that was only ever true in the TSDoc before this fix.
- **B1 (data-loss fix, most important one)**: `claudemd`/`mcp` are whole-file-replace writers (unlike `hook`/`permission` which merge) — a pre-existing non-empty target now gets backed up to `~/.nakiros/<projectId>/bootstrap-backups/<runId>/<filename>` via new `backupIfNonEmpty()` in `bootstrap-dispatch.ts` before the writer runs. `dispatchProposal`/`dispatchBootstrapPlan` signatures grew `projectId`/`runId` params to namespace the backup dir — this is a breaking signature change for anyone else calling these two exports directly (none did, at time of writing). Verified live with a tsx dry-harness (temp dir, real pre-existing CLAUDE.md, confirmed backup content matches original before overwrite).
- **B2 (data-loss fix)**: new `archiveBootstrapPlanOnStop()` in bootstrap-runner.ts, called from `cleanupOnTerminal` whenever `run.plan` exists AND `run.status !== 'completed'` — writes `plan.json` + `run-summary.json` to `~/.nakiros/<projectId>/bootstrap-plans/<runId>/` before `cleanupRunWorkdir` rmSync's everything. Mirrors `audit-runner.ts`'s `archiveReport` rescue-before-delete pattern (same pattern, new location convention — no existing archive dir name fit, called it `bootstrap-plans/` not `bootstrap-audits/` since there's no audit concept here). No retrieval IPC channel yet — purely a safety-net file, not surfaced in any UI. A future "past bootstrap attempts" screen could read from here.
- **B3 (two-part fix)**: (a) new `getResumableBootstrapWorktreePaths()` export in bootstrap-runner.ts, unioned with eval's `getResumableSandboxPaths()` in `server.ts`'s `sweepOrphanSandboxes()` call — **found in passing that audit/fix/create/edit have the exact same gap** (their worktrees aren't in this keep-set either, only eval's are) but that's NOT fixed here, out of scope per the coordinator's B3 wording (bootstrap-only). (b) `rehydrate()` now checks `existsSync(blob.cwd)` and drops `cwd` (not the whole run) when the worktree is gone — approval/dispatch never touch `cwd` so this never blocks approving an already-good plan, only degrades future discuss-turn spawns to use `workdir` instead (always present, so no ENOENT).
- **B5**: `rehydrate()` maps persisted `'executing'` → `'failed'` + `interruptedByReboot: true` + explanatory error, plan preserved. Was previously a silent pass-through (not in the `wasActive` branch, not in the early `stopped`/`failed` cleanup branch) — a genuine zombie state before this fix.
- **B8**: extracted `apps/nakiros/src/services/runner-core/chat-timeline-builder.ts` (`buildChatTimeline` + `ExcludedToolPathPredicate`) from `audit-runner.ts`'s `getAuditTimeline` and `bootstrap-runner.ts`'s `getBootstrapTimeline` — both were ~90% identical. Both now delegate, passing their own `isAuditProgressPath`/`isBootstrapPlanPath` predicate (kept as module-private functions in each runner, only the loop+sort logic moved). **Explicitly did NOT touch fix-runner's older copy** per the coordinator's instruction ("leave for a later pass") — if that pass happens, `fix-runner.ts`'s timeline builder is the next candidate for this same extraction, but it also emits fix-specific kinds (`edit`/`finding`/`eval_result`) so it needs a different integration shape (extend the base, not just swap the loop).
- **B9**: `listActiveBootstrapRuns`/`listAllBootstrapRuns` now map through a new module-private `toListSummary()` that returns a **copy** with `plan: null, turns: [], proposalCount: run.plan?.proposals.length` — critically does NOT mutate the live `entry.run` object (would corrupt the in-memory run for subsequent turns). `getBootstrapRun`/the event stream still return the full object. Relies on `BootstrapRun.proposalCount?: number` which the coordinator added to `packages/shared/src/types/project-bootstrap.ts` and rebuilt dist for, before this round started.
- **B10 (deferred, as instructed)**: synchronous `git worktree add` in `prepareWorkdir` and synchronous dispatch in `approveBootstrapPlan` both block the Fastify request thread — pre-existing runner-core-wide pattern (audit/fix/create/edit already do the same), not something introduced by bootstrap. Fixing it for bootstrap alone would mean either (a) a runner-core-wide async refactor (explicitly out of bounds per the coordinator) or (b) making `approveBootstrapPlan`'s dispatch fire-and-forget, which breaks the frontend's synchronous "call approve → get the final run back" expectation — the frontend agent wasn't briefed on that contract change, so didn't attempt it mid-parallel-work. Left as-is, documented as deferred only.
