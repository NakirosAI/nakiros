**Design decisions specific to this runner (read before touching it again):**
- Worktree IS used (mirrors audit-runner) even though the skill never writes to the project — chosen because `writeExecutionSettings` writes `.claude/settings.local.json` into whatever dir the agent's cwd is, and writing that into the REAL project directory would leave a stray Nakiros file in the user's repo. A worktree is a disposable checkout, safe to write into and destroy.
- **Found and avoided a latent bug in `audit-runner.ts`**: it writes `dot-claude-snapshot.json` into `workdir` unconditionally, even when a worktree exists and `run.cwd` (the agent's actual cwd) is the worktree — the file would be invisible to a relative `Read` from the agent. Confirmed by grep: no `buildCliArgs`/`--add-dir` override compensates for this in audit-runner. NOT fixed there (out of scope, regression risk) but bootstrap-runner correctly writes `dot-claude-snapshot.json` AND `friction-digests.json` into `contextDir = worktreePath ?? workdir` — i.e. wherever the agent's cwd actually resolves to. If a future runner copies audit-runner's snapshot-writing block verbatim, watch for this.
- No progress-polling timer (unlike audit's `afterStart` + `syncTimer` on a 1s interval for its incremental `outputs/audit-manifest.json`+`audit-progress.jsonl`). The `nakiros-project-bootstrap` skill writes a single `plan.json` once per turn (full rewrite, not incremental), so `onTurnComplete` reads it once — no interval needed. Real simplification vs audit, not a corner cut.
- Status-transition signal is `plan.json`'s `generatedAt` timestamp changing (or first appearance) vs staying identical — mirrors audit's binary artefact-presence decision (`archiveReport` succeeds or not) but adapted since bootstrap's artefact exists on every turn, not just the last one. Changed → `awaiting_approval` (custom transition, not one of `PostTurnHelpers`' three — mirrors `helpers.wait()`'s internals by hand, same pattern needed for any future custom status). Unchanged → `helpers.wait()` (agent asked a real clarifying question).
- `canSendUserMessage` overridden to accept BOTH `waiting_for_input` AND `awaiting_approval` — the user can discuss at any point before clicking Approve, not just when the agent explicitly asked something.
- **Execution seam (step 5 boundary, deliberate)**: `approveBootstrapPlan()` applies decisions to `plan.proposals[].status` (`accepted`/`rejected`, optional `content` override + `editedAt`), transitions the run to `executing`, then calls internal `dispatchApprovedProposals()` — currently a **no-op stub** (just logs the accepted count). The run stays parked in `executing` — no proposal ever reaches `written`/`failed` yet, no sister expert is invoked, nothing false is claimed. User can still `stop()` an `executing` run (works with no live child process). Step 5 replaces only `dispatchApprovedProposals()`'s body; nothing else in the file needs to change. This was a judgment call the coordinator explicitly delegated — chose "honest stuck state, stoppable" over "silently auto-complete."
- Friction-digest enrichment: `writeFrictionDigestsIfAvailable()` gates on `isHookInstalled() && isWatcherRunning()` (global ingest-enabled check — no per-project variant exists in the codebase) + `listDigestsForProject(projectPath)` returning at least one `status:'ready'` digest with `frictionCount > 0`. Writes `friction-digests.json` (`{ projectPath, generatedAt, sessionCount, digests: ConversationDigest[] }`, newest-first, capped at 20) into `contextDir`. **No aggregate-across-sessions file exists anywhere in the codebase** — confirmed by research; `{project}/.nakiros/frictions/aggregate.json` referenced in `nakiros-claudemd-expert`'s SKILL.md is aspirational/unimplemented ("schema TBD" per its own comment). Corrected the step-2 skill's `SKILL.md` + `references/codebase-signals.md` to point at the real `friction-digests.json` contract instead of copying that unimplemented convention.
- `findActiveForTarget` disambiguates by `projectId` only (one active bootstrap run per project — simpler than audit's multi-`*Target` disambiguation since bootstrap has no sub-target).
- Sweep-safety in `server.ts`: `collectLiveProjectEntryNames()` protects BOTH `run.cwd` and `run.workdir` for bootstrap runs (audit/fix/create/edit only protect `run.workdir` there even though they can have a worktree `cwd` too — likely a pre-existing gap, not fixed, just not copied).
